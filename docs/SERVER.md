# نصب سرور مشترک

سرور فقط API، MCP و فایل گزارش محافظت‌شده دارد؛ پنل مدیریتی یا نیاز به ورود OpenAI ندارد. جمع‌کنندهٔ هر کامپیوتر، آمار خودش را به این سرور می‌فرستد.

## نصب تعاملی روی Linux با systemd

روی **همان سروری که برای نصب انتخاب کرده‌اید**:

```sh
git clone https://github.com/AlirezaDadrass/codex-token-monitor.git
cd codex-token-monitor
git checkout v0.1.0
sudo bash scripts/install-server.sh
```

نصب‌کننده به‌ترتیب این موارد را می‌پرسد:

1. نام مرکز.
2. آدرس گوش‌دادن؛ پیش‌فرض `127.0.0.1` برای تونل SSH یا reverse proxy.
3. پورت؛ پیش‌فرض ۸۷۸۷.
4. آدرس سرور برای اتصال کامپیوترها، مانند `https://monitor.example.com`.
5. توکن موجود، به‌صورت مخفی؛ اگر خالی بگذارید، توکن جدید ۲۵۶ بیتی ساخته می‌شود.
6. مسیر گواهی TLS مستقیم، در صورت نیاز؛ سپس مسیر کلید خصوصی.

سپس باینری همان نسخه را از GitHub Release دریافت می‌کند، SHA-256 را بررسی می‌کند، یک کاربر محدود می‌سازد و سرویس بومی systemd را فعال می‌کند. Go، Docker، PostgreSQL و Redis برای اجرای سرور لازم نیستند. ابزارهای پایهٔ `curl`، `tar`، `sha256sum`، `useradd`، `getent` و `systemctl` باید موجود باشند. معماری دانلود خودکار Linux برابر amd64 یا arm64 است.

برای پیش‌نمایش بدون تغییر فایل، کاربر یا سرویس:

```sh
bash scripts/install-server.sh --dry-run
```

برای استفاده از فایل اجرایی که خودتان ساخته/بررسی کرده‌اید:

```sh
go build -trimpath -o bin/token-monitor ./cmd/token-monitor
sudo bash scripts/install-server.sh --binary "$PWD/bin/token-monitor"
```

برای نسخهٔ دیگر، `--version vX.Y.Z` بدهید. اسکریپت روی تنظیمات یا سرویس موجود نصب مجدد انجام نمی‌دهد؛ نام و توکن نصب قبلی را بازنویسی نمی‌کند.

## فایل‌ها و سرویس

| مورد | مسیر |
| --- | --- |
| فایل اجرایی | `/usr/local/bin/token-monitor` |
| تنظیمات | `/etc/codex-token-monitor/config.json` |
| توکن | `/etc/codex-token-monitor/hub-token` |
| داده و گزارش‌ها | `/var/lib/codex-token-monitor` |
| سرویس | `codex-token-monitor.service` |
| کاربر سرویس | `codex-token-monitor` |

تنظیمات و کلید، متعلق به root و فقط برای گروه سرویس قابل خواندن هستند. سرویس بدون دسترسی root و با دسترسی نوشتن محدود به پوشهٔ داده اجرا می‌شود. توکن در خروجی، unit یا آرگومان پردازش قرار نمی‌گیرد. مقدار آن را از مسیر خصوصی بالا برای دستگاه‌های موردنظر فراهم کنید؛ در گفتگو، issue یا ریپوی عمومی قرار ندهید.

```sh
sudo systemctl status codex-token-monitor.service
sudo journalctl -u codex-token-monitor.service -n 50 --no-pager
```

فعال بودن unit، بررسی دسترسی بیرونی یا درست بودن DNS/TLS را اثبات نمی‌کند. از یک دستگاه مقصد با توکن واقعی نصب کلاینت را اجرا کنید؛ نصب‌کنندهٔ کلاینت اتصال احرازشده را بررسی می‌کند.

## دسترسی شبکه

سه روش متداول:

- **تونل SSH:** سرویس روی `127.0.0.1:8787` بماند. روی هر کامپیوتر `ssh -N -L 8787:127.0.0.1:8787 USER@SERVER` را باز نگه دارید و آدرس `http://127.0.0.1:8787` را به کلاینت بدهید.
- **TLS مستقیم:** آدرس گوش‌دادن قابل دسترس و گواهی معتبر ارائه دهید. مسیر گواهی و کلید به پوشهٔ تنظیمات کپی می‌شوند. برای تمدید، فایل‌های کپی‌شده را با مالکیت/دسترسی درست به‌روز و سرویس را restart کنید.
- **Reverse proxy HTTPS:** سرویس روی loopback بماند و دامنه را در Nginx/Caddy موجود به آن وصل کنید. `public_url` در تنظیمات باید آدرس HTTPS قابل دسترس کاربران باشد تا لینک گزارش هم درست ساخته شود. هدر Authorization را حفظ و buffering مربوط به MCP را درست تنظیم کنید.

اسکریپت فایروال، DNS، reverse proxy یا پورت‌های سرویس‌های موجود را تغییر نمی‌دهد. پورت سرویس باید بین ۱۰۲۴ و ۶۵۵۳۵ باشد؛ برای ۴۴۳ از reverse proxy استفاده کنید. HTTP ساده را فقط روی loopback یا شبکهٔ رمزگذاری‌شده استفاده کنید؛ برای اینترنت، HTTPS لازم است.

همهٔ APIها از جمله `/health` و `/mcp` توکن Bearer می‌خواهند. مسیر `/reports/...` فقط با همان توکن یا امضای محدود یک‌ساعته برای همان فایل قابل دریافت است. مقدار اصلی توکن در لینک گزارش نیست.

## اتصال دستگاه‌ها

روی هر کامپیوتر فایل اجرایی را آماده و اجرا کنید:

```sh
token-monitor install
```

نام دستگاه، آدرس سرور و توکن را وارد کنید. این همان فرایندی است که [ایجنت هم می‌تواند انجام دهد](AGENT_INSTALL.md). نام دستگاه و شناسهٔ آن باید برای هر نصب مستقل باشند. نام `account` در همهٔ پروفایل‌ها باید یکسان باشد؛ پیش‌فرض `personal` است. `expected_machines` در تنظیمات سرور تعداد مورد انتظار را مشخص می‌کند؛ پیش‌فرض ۳ است.

سرور خودش جای جمع‌کنندهٔ کامپیوترها را نمی‌گیرد. هر دستگاه باید MCP محلی یا `watch` فعال داشته باشد. اگر روی خود سرور هم از Codex استفاده می‌کنید، برای کاربر واقعیِ Codex یک پروفایل کلاینت جدا نصب کنید؛ پروفایل systemd سرور را به لاگ‌های شخصی متصل نکنید.

## ارتقا، توکن و حذف

- **ارتقا:** فایل اجرایی نسخهٔ جدید را دریافت، checksum را بررسی و جایگزین کنید؛ سپس سرویس را restart کنید. قبل از تغییر نسخه، پوشهٔ تنظیمات و داده را پشتیبان بگیرید. اسکریپت نصب اولیه برای بازنویسی نصب موجود طراحی نشده است.
- **تعویض توکن:** فایل `hub-token` را با مقدار جدید و همان مالکیت/دسترسی جایگزین کنید؛ سرویس و کلاینت‌ها را هماهنگ restart کنید. تمام لینک‌های امضاشدهٔ قبلی هم نامعتبر می‌شوند. توکن فعلی را در خروجی چاپ نکنید.
- **پشتیبان:** پوشه‌های `/etc/codex-token-monitor` و `/var/lib/codex-token-monitor` کافی‌اند. پوشهٔ تنظیمات شامل secret است و باید خصوصی بماند.
- **توقف:** `sudo systemctl disable --now codex-token-monitor.service` سرویس را متوقف می‌کند و داده را نگه می‌دارد. حذف داده/کاربر/فایل‌ها را جداگانه و فقط بعد از تصمیم به حذف دائمی انجام دهید.

## میزبان بدون systemd

همان باینری را بومی اجرا کنید و مدیریت پردازش را با روش متداول همان میزبان انجام دهید:

```sh
token-monitor init --name Hub --create-token --public-url https://monitor.example.com
token-monitor hub --listen 127.0.0.1:8787
```

برای اجرای دستی، همان فایل تنظیمات کاربر استفاده می‌شود. اگر مسیر سفارشی تعیین می‌کنید، در هر دو فرمان `--config /path/config.json` بدهید. این اسکریپت روی macOS/Windows سرویس سیستمی نصب نمی‌کند؛ باینری با `hub` قابل اجرا است.

اسکریپت با بررسی نحو و حالت dry-run آزموده می‌شود؛ اجرای کامل systemd باید روی سرور مجاز خودتان انجام و همان‌جا بررسی شود.
